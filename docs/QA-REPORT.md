4.3 QA Observation

The architecture correctly avoids using an LLM as a row-by-row synthetic-data generator.

## 6. Data Quality QA

6.1 Tabular Data

The implementation should verify:

Numeric distributions.
Categorical proportions.
Missing-value rates.
Outlier behavior.
Relevant correlations.
Seed reproducibility.
Privacy configuration.
6.2 Relational Data

The implementation should verify:

Primary-key uniqueness.
Foreign-key validity.
Zero orphaned references.
Configured cardinalities.
Cross-table consistency.
Business relationships.

Example:

Customers
↓
Orders
↓
Order Items

An order must not reference a non-existent customer, and an order's calculated total should reconcile with its line items.

6.3 Documents
Invoices

Verify:

Subtotal

- Tax
- Applicable Charges
  = Total

The exact formula depends on the configured invoice rules.

Bank Statements

Verify:

# Current Balance

Previous Balance

- Credits

* Debits

The implementation must handle the selected transaction conventions consistently.

## 13. Defect Classification

Critical

Blocks core functionality or produces invalid synthetic data.

Examples:

Broken FK integrity.
Incorrect invoice totals.
Incorrect bank balances.
Invalid generated schema.
Exporting failed/invalid data.
High

Major feature failure without necessarily corrupting all generated data.

Examples:

Tabular engine failure.
Document generation failure.
AI schema inference failure with no fallback.
Broken frontend/backend integration.
Medium

Important usability or non-core functionality issue.

Examples:

Preview problems.
Configuration UI inconsistencies.
Non-critical export issue.
Low

Minor visual or usability issue that does not affect core functionality.
